# Bug hunt — 2026-08-12

Six independent lenses swept the codebase twice; every finding then faced three skeptics (is the code wrong / can a real drummer reach it / does a test already prove it right) and survived a majority vote. 29 defects confirmed.

## P0 — 9

### downloadSong.ts skips the audio-presence gate that every other song-loading path enforces

`src/main/ipc/downloadSong.ts:145`

**Why it breaks:** After unpacking a downloaded .sng and calling buildSongFromDir, downloadSong.ts only checks `!songData.drumDifficulties?.length` before storing the song and replying `success: true`. It never checks `songData.audio.length === 0`, unlike every sibling caller of buildSongFromDir: importSong.ts's validateSongDir (line 37: `if (song.audio.length === 0) throw ...`), splitSong.ts (line 56: `!songData || songData.audio.length === 0`), and playability.ts (line 87: `song.audio.length === 0`). This is proven empirically: downloadSong.test.ts's shared VALID_SONG fixture (song.ini + notes.chart only, zero audio files) is used by the 'writes the unpacked song, persists it and replies success' test, which asserts `success: true` and passes (`corepack yarn vitest run src/main/ipc/downloadSong.test.ts` -> 9/9 passing) even though the resulting SongData has an empty audio array.

**What he experiences:** Downloading a reviewed Chorus Encore package whose .sng doesn't yield a matching .ogg/.opus/.mp3 file (corrupted archive, unsupported stem format, or a server-side packaging gap) silently succeeds: the song is written to disk, stored in appState, and returned to the renderer as a normal song with no error. Because SongListItem.tsx's `playable` flag (see finding 2) never checks audio either, this song then renders as a normal clickable, playable library row — the user only discovers it's broken when they start practice and there is no audio to play.

### Unscoreable false hits are still persisted as scored 'wrong' evidence, corrupting mastery quality

`src/renderer/services/engine/engine.ts:173`

**Why it breaks:** judge.ts's maybeRecordFalseHit (judge.ts:332-391) computes a local `scoreable` flag: a strike inside a silent/rest region that isn't close to any real note is deliberately excluded from `falseHitTicks` (judge.ts:348-353) so it 'doesn't tank the score' per the comment at judge.ts:339-346. But `falseHitListeners` still fire for it whenever the tick has a containing measure (judge.ts:356-358, proven by the existing passing test 'still shows a false hit made inside a fully silent measure' at judge.test.ts:663). The emitted `FalseHitRecord` (types) never carries the `scoreable` bit at all -- only the separate `ResolvedJudgement.scoreable` field does. Engine's onFalseHit handler (engine.ts:173-201) has no way to see `scoreable` and unconditionally pushes a `verdict: 'wrong'` HitRecord into `runRecords`/`attemptRecords` for any kit element. I proved this empirically: added a test with a lone all-rest measure (no other notes, so no note is ever 'near'), struck it once -- `judge.falseHitCount` was 0 (correctly not scoreable) yet `engine.getRunRecords()` contained a full `{verdict:'wrong', element:'crash'}` record (reverted after verification). This corrupts `RunSummary.totalWrong`/`computeWrongHitCounts` (compute.ts:140-157), which feed `src/renderer/services/pedagogy/skill-state.ts:111-113`'s `correct_lane_rate = totalHits/(totalHits+totalWrong)`, a direct 15% component of the mastery `quality` score gating whether a pass counts (skill-state.ts:85-89, `isQualifyingPass`). The live in-session tutor detector is unaffected (it correctly filters on the judgement channel's own `scoreable` flag, tutor/detector.ts:29,45), but the persisted evidence path is not.

**What he experiences:** An incidental warm-up tap, fill, or off-beat cymbal choke during a rest -- something Judge and the live on-screen score explicitly decide should not count against him -- still gets permanently recorded as a wrong-pad strike in the run's evidence, lowers his per-lane wrong-hit tally on the results screen, and measurably drags down the mastery/ZPD quality score for that song, potentially denying credit for an otherwise clean pass. This is the same class of 'pedagogy punishes a good pass' problem as the tempo-cut-at-100%-accuracy bug that was already fixed elsewhere in this tree.

### Tutor evidence for a measure is never invalidated by a rewind, and deterministic judgement ids make a stale miss permanent

`/Users/konstantinbaltsat/sightkick/src/renderer/services/tutor/machine.ts:127`

**Why it breaks:** recordJudgement dedupes purely by judgement.id (`existing.some((item) => item.id === judgement.id)`), and Judge generates that id as `note:${tick}:${prefix}` (judge.ts:218-220, used for both 'hit' at judge.ts:536 and 'miss' at judge.ts:285) - deterministic by chart position alone, not by which pass produced it. `judgementsByMeasure` is only ever cleared by the tutor's own recovery machinery (`clearJudgements` inside beginRecovery/finishRecoveryAttempt); useTutorSession.ts never subscribes to `engine.onReset` (confirmed absent; contrast with the sibling hook useRemediationSession.ts:172-174, which does subscribe and resets its own counters). So any rewind the tutor didn't itself initiate leaves stale judgements standing. The newest shipped feature, self-directed loop-drag drilling, hits this exactly: usePracticeSession.ts:93-111 drives engine.setLoopRegion from the user's dragged practiceRange while gameMode==='practice' (the same mode the tutor runs in, SongView.tsx ~1487 `enabled: gameMode === 'practice' && adaptiveTutorEnabled`); every natural loop wrap calls transport.ts's playFromTick, which unconditionally fires onSeek (transport.ts:254); engine.ts's onSeek handler (line ~120-143) rewinds Judge state and fires the (tutor-unheard) reset listeners. On the next loop pass the same notes get the same ids, so a corrected hit is emitted with the identical id as the earlier miss and is silently dropped by the dedup check, leaving the stale miss as permanent evidence for that measure. Proven empirically: a machine-level probe (dispatch judgement(measure0,offset0,'miss') then judgement(measure0,offset0,'hit')) left `state.judgementsByMeasure[0]` at length 1 with verdict 'miss' - the corrected hit never registers.

**What he experiences:** Playing a hard bar in a self-directed drill loop (loop-drag a range, miss a few notes on pass 1, then nail it cleanly on passes 2-10) leaves the tutor's per-measure evidence frozen at the bad first-pass numbers no matter how well the player subsequently performs. detectTutorTrigger reads exactly this frozen evidence, so it can fire a material-failure/begin-recovery takeover (pause playback, forced rewind to a checkpoint) against a player who has already been hitting the passage correctly for several loop passes - the same 'tutor punished me while I was playing correctly' failure class already fixed once for the single-stray-wrong-pad case. Even when the trigger threshold isn't crossed, the persisted learning evidence for that bar stays permanently wrong (a miss that was actually corrected), corrupting anything downstream that reads intervention/recovery history.

### deriveMisses() fabricates misses for notes never reachable in the current playthrough, corrupting any mid-song-start run that reaches a natural end

`src/renderer/services/engine/engine.ts:670`

**Why it breaks:** deriveMisses() (called from handleEnded()) iterates every note in the whole chart and marks anything not judge.isHit() as a miss, with no lower bound at the tick this Engine/Judge instance's playback actually started from. playFromTick(tick) never seeds the Judge with an out-of-scope boundary before tick, so when a fresh Engine begins mid-song (no loop region set) and later reaches the real end, every note before the start tick — which the player never had a chance to play this session — is reported as a genuine miss. Empirically reproduced with an isolated Engine test: two notes at ticks 480/960, playFromTick(960), hit only the second note, then natural end -> persisted summary came back totalMisses: 1 for the untouched, out-of-range note at 480. Two production call sites trigger this with no loop set: resuming an interrupted checkpoint (SongView.tsx:1649, playRunFromTick(interruptedResumeTick, 'force')) and clicking a measure to scrub-and-continue (SongView.tsx:2816). The existing zero-hit persistence gate (decideRunEvidence in evidence.ts) does not catch this because the resumed/scrubbed run has real hits in the tail segment, so persistEligible and rewardEligible are both true.

**What he experiences:** Every time the user resumes an interrupted practice attempt, or clicks a bar in the notation to continue playing from there to the end, the saved run is padded with fake misses for every note before that point. totalHits/totalMisses/overallAccuracy/laneAccuracy/timingBias are all wrong for that run, and the corrupted summary is durably saved and used for XP, streak, mastery decay, and Coach findings — silently making a legitimate partial-song pass look like he missed a whole section he never attempted.

### Input-latency compensation ignores playback speed

`src/renderer/services/engine/judge.ts:327`

**Why it breaks:** compensateLatency() subtracts `this.latencyMs / 1000` directly as chart-domain (song-time) seconds. But the `rawTick` it receives comes from Transport, whose position is `audioPlayer.currentTime = (ctx.currentTime - startedAt) * playbackSpeed + offset` (transport.ts:493-494 driving TimeStore; speed/player.ts:349-365) — song-time advances at `playbackSpeed` times wall-clock speed. A fixed wall-clock hardware delay of L ms therefore corresponds to `L * playbackSpeed` ms of song-time drift, not a flat L ms. The engine's own SpeedAudioPlayer.currentTime getter gets this right for OUTPUT latency two lines away (`latency * this._playbackSpeed`, speed/player.ts:360-362) — an internal precedent proving the multiplication is the intended fix elsewhere in this exact class — but Judge's INPUT-latency compensation never receives playbackSpeed at all (grep across judge.ts/judge.test.ts/types.ts finds zero references to speed). At speed 0.5x a 100ms calibrated latency setting overcompensates song-time by 50ms; at 2x it undercompensates by 100ms. No test exercises setLatencyMs together with setPlaybackSpeed: judge.test.ts's latency tests (lines ~778-812) and engine.test.ts's speed tests (lines 314-335, 895) never overlap.

**What he experiences:** Any player who calibrates 'Input Latency' in Settings (InputConfig.tsx, up to +-200ms, described as compensating 'a laggy pad or interface') and then practices at anything other than 1x — which is the app's own recommended beginner range (0.5x-0.7x) — gets systematically wrong hit/miss judgments and wrong stored timing-bias analytics: genuinely on-time strikes can land outside the hit-tolerance window (100ms Perform / 180ms Practice) and get recorded as misses, or the reverse at speeds above 1x. This is exactly the 'recorded misses on real hits' failure class called out in the task background.

**Why it breaks:** Transport.setPlaybackSpeed (transport.ts:133-146) calls SpeedAudioPlayer.setPlaybackSpeed (speed/player.ts:70-88), which while already playing synchronously calls `this.start(resumeAt, ...)`. start() (lines 141-200) begins by synchronously calling `this.stop()` (line 142-144, since isInitialised is still true) which sets `startedAt = -1`, `isInitialised = false`, bumps `epoch` (stop(), lines 337-347) -- all BEFORE the function yields at `await this.prepared` (line 151). **What he experiences:** An entirely ordinary sequence -- nudge playback speed, then hit pause soon after -- leaves the UI showing 'parked'/paused with the playhead reset to bar 1, while the actual audio keeps sounding from wherever it was at the new speed until the user notices. ### Removing a single default-mapped MIDI note wipes the entire lane's default mapping

`src/renderer/context/InputContext.tsx:369`

**Why it breaks:** For a kit lane that has never been explicitly configured for the current device, `inputMappings[selectedDevice.id]` has no entry for that element, so `prev[selectedDevice.id]?.[element]` is `undefined`. `removeControl`'s kit branch computes `without(undefined ?? This is the same failure signature as the already-fixed 'seven misses and zero hits' bug, now reachable through the Learn/remove UI on any never-touched lane instead of a race condition.

### Remapping a MIDI note to a new lane leaves it silently active on its old default lane too

`src/renderer/context/InputContext.tsx:121`

**Why it breaks:** `assignInto`'s dedupe only strips the controlId out of keys already present in `current` -- the persisted, per-device stored mapping -- never out of `DEFAULT_MIDI_INPUT_MAPPING` entries that a lane is still falling back to because it was never explicitly stored (per the comment at lines 110-115, this is deliberate, to avoid blanking untouched lanes). But the effect is that a note can never be *moved off* its default lane, only *added* to a new one. Verified with a live repro: after `setSelectedDevice(DEVICE_A)` then `assignControl('tom1','midi:38')` (Learn tom1 <- note 38, the pad's default snare trigger), `inputMapping.tom1` correctly contains `midi:38`, but `inputMapping.snare` still contains it too. Judge.handleInput builds `expectedPrefixes` by unioning every mapping entry that includes the struck controlId (judge.ts:398-406), so a strike on that one physical pad now matches both lanes' chart keys. `resolveElement` (judge.ts:315-319) returns only the first matching element in mapping key order (snare precedes tom1 in the fixed `EMPTY_INPUT_MAPPING` key order), so even a correct tom1 hit gets attributed and recorded as a snare hit -- and if a chart note is a chord containing both lanes' keys at the same tick, the single physical strike passes the per-key filter for both prefixes and records two separate HitRecords (engine.ts's onHit handler pushes one record per prefix in `newPrefixes`) for one physical strike.

**What he experiences:** Any player who re-learns a MIDI note away from its Yamaha DTX/GM default onto a different drum lane -- an entirely normal setup action for this app's single target user tuning his kit's pad mapping -- keeps silently crediting the old lane from that pad indefinitely. A tom hit can be scored (and persisted into practice-stats evidence) as a snare hit, a wrong-pad strike is never flagged wrong because the stale default lane absorbs it as 'correct', and on chord notes a single strike can double-count as two separate hits.
