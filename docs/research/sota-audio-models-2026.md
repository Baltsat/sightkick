# SOTA open-source audio models for drum charting (2026)

Research date: 2026-08-05. Scope: best open-source models for (1) music source separation, (2) automatic drum transcription (ADT), (3) beat/downbeat/tempo tracking, and (4) YouTube audio acquisition — for SightKick (Electron, macOS Apple Silicon M1 Pro / 32GB RAM).

**Context found while grounding this research:** the app's current stem splitter is confirmed via [`tonygoldcrest/sightkick-tools`](https://github.com/tonygoldcrest/sightkick-tools) README to wrap **Demucs** (variant unspecified in the README) packaged as a PyInstaller standalone binary (no Python required), MIT-licensed. Separately, `src/main/ipc/autoChart.ts` in this repo shows the shipped "AutoChart" feature actually drives a **different, proprietary local tool called OCTAVE/STRUM** (external macOS app with its own onset-classifier checkpoints for drums _and_ guitar/bass/keys) — not ADTOF-pytorch directly. That tool is closed-source and out of scope for this OSS survey; it's noted here so the recommendation below is understood as "what to evaluate as a replacement/upgrade path," not a description of what autoChart.ts calls today.

Treat MVSep numbers as directionally useful for model ranking, not as apples-to-apples with the MUSDB18-HQ figures in papers.

### 1b. Practical packaging: `python-audio-separator`

[`nomadkaraoke/python-audio-separator`](https://github.com/nomadkaraoke/python-audio-separator) (MIT) wraps Demucs v4, MDX-Net (ONNX), VR Arch, and MDXC/Roformer models behind one CLI/Python API with **automatic model download** (no manual checkpoint hunting) and a `--list_models --list_filter=drums` command that prints exactly the per-stem SDR table used above. Confirmed **Apple Silicon support**: "Apple Silicon, macOS Sonoma+ with M1 or newer CPU (CoreML acceleration)" via `pip install "audio-separator[cpu]"`, with CoreML/ONNXRuntime acceleration for the MDX-Net/Roformer paths (Demucs itself runs via PyTorch, CPU or — with caveats below — MPS). This is the recommended integration point: swap `htdemucs_ft` for a Roformer checkpoint later without changing the calling code.

**Native Apple Silicon alternative:** [`ssmall256/mlx-audio-separator`](https://github.com/ssmall256/mlx-audio-separator) ports `audio-separator`'s inference paths to Apple's **MLX** framework (no PyTorch/ONNXRuntime at inference time). Its own README benchmark (12-song MUSDB18-HQ subset on an M4 mini) claims **1.4×–2.5× speedup** over the standard `audio-separator` path depending on model. Caveat: this is a **10-star, single-maintainer, ~2-month-old project** (as of this research) — promising for a future perf pass, not yet something to depend on for a shipping product.

**Demucs + MPS gotcha:** standard Demucs does **not** work with PyTorch's MPS backend — complex tensors and custom ops in the architecture are incompatible, per user reports on the [official demucs issue tracker](https://github.com/facebookresearch/demucs/issues/432). Expect **CPU-only** Demucs inference on M1 Pro (roughly 1.5× track duration per the official README) unless you move to the MLX port above.

## 4. YouTube audio acquisition & existing OSS "YouTube → chart" pipelines

- **[yt-dlp](https://github.com/yt-dlp/yt-dlp)** remains the only credible OSS choice; it's what your `fetchOfficialYoutubeMetadata`/`canonicalizeYoutubeUrl` code in `autoChart.ts` is presumably feeding into downstream. Key 2026 operational notes from the [yt-dlp wiki](https://deepwiki.com/yt-dlp/yt-dlp-wiki/3.2-youtube-authentication):
  - YouTube is progressively requiring **PO tokens**; yt-dlp can't generate them itself, so by default it sticks to client variants that don't need one, at the cost of some formats being unavailable. If you hit failures, the documented fallback is the `mweb` client + an externally supplied PO token.
  - Age-restricted content: yt-dlp tries `web_embedded` (works if the video is embeddable) then `web_creator` (may require login) — there's no guaranteed bypass without authentication, and authenticating with a real account risks that account being flagged.
  - Throttling: use `--sleep-requests` / concurrent-fragment downloads, and treat `429`/`402` errors as IP-block signals, not bugs to retry aggressively.
  - **Keep yt-dlp on auto-update** — YouTube's countermeasures shift often enough that pinning a version is a recurring support burden, more than most dependencies.

- **Chained YouTube→stems→chart OSS projects worth looking at rather than re-building:**
  - **[rtribbia/chartster](https://github.com/rtribbia/chartster)** — converts Songsterr drum tabs to Clone Hero charts, auto-aligned to a YouTube audio track (not audio-driven transcription, but solves the YouTube-alignment problem you also have).
  - **[jackwallner SongHero](https://jackwallner.com/songhero/)** — closest conceptual match ("any song → playable Clone Hero chart"), but pulls audio via Spotify link and uses a closed LLM (Gemini 2.0 Flash) for section-aware note placement — worth studying the UX/output-format choices, not reusable as an OSS dependency for the ADT step itself.
  - **[EFHIII/midi-ch](https://github.com/EFHIII/midi-ch)** and **[bumpmann/chsplicer](https://github.com/bumpmann/chsplicer)** — MIDI-to-Clone-Hero-chart and difficulty-reduction tooling; useful for the _last mile_ (MIDI events → `.chart`/`.mid` file with difficulties) once you have transcribed notes, regardless of which ADT model produces them.
  - No project was found that already chains open-source stem separation + open-source ADT + chart-file emission end-to-end with a permissive license — this remains the gap SightKick would be filling.

## Risks / gotchas

1. **ADTOF (today's ADT model) is CC BY-NC-SA 4.0 — non-commercial.** This covers both the code and any pretrained weights/data in the [MZehren/ADTOF](https://github.com/MZehren/ADTOF) repo. If SightKick is or becomes a paid product (or even ad-supported/monetized in any way), shipping ADTOF-derived transcription needs either a separate license from the authors or a switch to a permissively-licensed alternative. This is the single biggest license risk found in this research.
2. **`madmom`'s pretrained models/data are CC BY-NC-SA 4.0** even though its source code is BSD. Any tool that depends on madmom for its DBN postprocessing (BeatNet's offline mode, `allin1`) inherits this restriction for the _model_ portion specifically — commercial use "requires contacting Gerhard Widmer" per the README. `Beat This!` sidesteps this entirely by design (no DBN needed) — another reason it's the recommended pick.
3. **LarsNet's pretrained weights are CC BY-NC 4.0.** Same non-commercial trap — usable for prototyping/evaluation, not for a shipped commercial feature, unless retrained on permissively-licensed data or relicensed by Polimi ISPL.
4. **The jarredou/aufr33 MDX23C DrumSep checkpoint has no formal license file from the original authors** — the HF mirror repo is tagged MIT, but that's the mirror repo's tag, not a confirmed grant from jarredou/aufr33 themselves. Reach out or find an explicit statement before depending on it commercially; this is the model the strongest recommendation (drum sub-stem separation) rests on, so it's worth resolving early.
5. **MT3 (Magenta) needs JAX/T5X**, which has no real GPU story on macOS (JAX's CUDA backend needs NVIDIA hardware) — CPU-only inference, and T5X's checkpoint restoration code is documented as flaky outside Linux/TPU/Colab. Don't invest here; YourMT3+ (PyTorch) is the practical multi-instrument-transformer alternative if that class of model is wanted.
6. **Demucs does not benefit from Apple's MPS backend** — complex tensors and custom ops in the architecture are incompatible with `torch.backends.mps` per reports on the official issue tracker. Expect CPU-bound inference (~1.5× track duration, per Demucs' own README) on M1 Pro unless/until you adopt an MLX-native port (small, early-stage community projects only exist today — `mlx-audio-separator` is 10 stars, ~2 months old).
7. **Large/awkward downloads**: LarsNet's pretrained checkpoints are ~562 MB; Demucs models range from tens to hundreds of MB per variant; sightkick-tools' current binary is already ~130 MB. Stacking a full pipeline (separation + drum-substem + ADT + beat tracking) could push a first-run download well past 500MB-1GB — budget for this in onboarding UX and consider lazy/on-demand downloads per stage, which `python-audio-separator` already supports natively.
8. **Python version pins**: `madmom`'s PyPI release is effectively capped below Python 3.10 for DBN features despite `setup.py` metadata claiming 3.12 support — a known, apparently unresolved gap between packaging metadata and reality. If any component in your stack pulls in madmom transitively (e.g. `allin1`), pin your embedded Python runtime accordingly or isolate that component in its own venv.
9. **No numbers here should be treated as final** without direct verification against the primary source before a go/no-go decision — several figures in this report came through third-party summarization of PDFs that could not be parsed directly (marked inline where that happened, e.g. the exact `beat_this` F-measure table, and some MVSep leaderboard entries which reflect a different, non-MUSDB18-HQ test set and so are not directly comparable to paper-reported SDR numbers).
10. **CUDA-only tooling**: most academic ADT/transcription repos (MT3, several diffusion-based ADT papers) assume an NVIDIA GPU implicitly in their example configs even when the underlying framework is technically cross-platform. Confirm CPU/MPS code paths exist before adopting, not just "framework runs on macOS in theory."
